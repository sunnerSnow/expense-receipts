# 0005. 月結匯出用 CSV,外幣只列原幣不換算台幣

- 狀態:Accepted
- 日期:2026-08-04

## Context(當時的情境)

Phase 3 要把該月已確認單據交給會計。roadmap 原本只寫「CSV/Excel + 影像打包」,
沒定格式細節,並註明「以會計實際需求為準,開工前先拿範本確認」。

同時 Phase 2 收尾時發現海外出差是實際情境(使用者提供了泰國 Starbucks、
McDonald's、Krispy Kreme、Lawson 的收據)。這些單據金額是 THB,而 `receipts.amount`
存的是原幣 —— 匯出清單要不要換算成台幣,是必須拍板的問題。

換算需要匯率,而匯率有好幾種都「正確」:信用卡實際入帳的台幣金額、當月平均匯率、
會計指定的表、交易日即期匯率。選錯不是小事,它直接影響帳上的費用金額與稅務。

## Decision(決定)

1. **匯出格式為 CSV**,UTF-8 帶 BOM、CRLF 換行 —— Excel 雙擊直接開且中文不亂碼,
   不引入 xlsx 套件。日後要加 xlsx,欄位組裝邏輯已在 core 可直接複用。
2. **外幣不換算台幣**。清單列「幣別」與「原幣金額」兩欄,台幣換算由會計依實際
   入帳成本自行處理。各幣別在清單尾端分別小計,不合併。
3. **匯出流程:先產檔、再 INSERT 批次紀錄**,而非「先建空批次再 UPDATE 補路徑」
   —— 這是為了守住鐵律 5(`export_batches` 只允許 INSERT)。
   批次紀錄與「單據轉 exported」在同一交易內完成。
4. **影像 zip 的檔名以清單流水號為前綴**(`007_AB12345678.jpg`),會計看清單第
   007 列就知道去 zip 找哪張,不必比對 UUID。

## 理由

- **系統猜匯率會產生「看起來精確但其實是猜的」數字**,比留空更危險 —— 會計可能
  直接採用而不查核。留原幣是誠實的做法:資料是單據上真實印的那個數字。
- 使用者明確表示匯率由會計計算。這本來就是報帳政策問題,不是技術問題。
- CSV 對自用規模夠用,而且會計要匯進其他系統時 CSV 反而最好處理。
- 先產檔再 INSERT 讓「批次存在」等於「檔案存在」,不會有半成品批次;
  若產檔失敗,DB 完全沒有痕跡,重跑即可。

## Consequences(代價與收穫)

- 收穫:匯出零外部依賴;不可逆的狀態轉換有交易保護;鐵律 5 不必開例外。
- 代價:有海外單據的月份,會計要自己加一欄換算 —— 這是刻意的分工。
- 代價:CSV 沒有欄寬、格式化、多工作表。若會計反映不好用再加 xlsx。
- 注意:匯出成功後單據進 `exported` 終態,**不可修改也不可刪除**(鐵律 5)。
  UI 已在匯出前顯示筆數與金額,並明確標示此操作不可逆。
- 注意:重複匯出同月不會重複帶走單據 —— 撈取條件是
  `status='confirmed' AND export_batch_id IS NULL`;web 端另用 pg-boss
  `singletonKey` 防連點。

## 被否決的替代方案

- **系統依匯率換算(使用者提供匯率)**:一度採用,但使用者確認匯率由會計計算,
  多做一個匯率輸入介面反而增加誤用空間(填錯匯率的數字看起來一樣可信)。
- **抓即時匯率 API 自動換算**:引入外部依賴,而且「哪一天的匯率」本身就是政策
  問題,自動化只是把決定藏起來。
- **xlsx 一步到位**:多一個相對重的依賴,而使用者尚未拿匯出檔給會計確認過格式。
  先用 CSV 驗證需求,再決定要不要投資。
- **匯出時就地產檔並直接回應下載**:單據轉終態需要交易保護,且大量影像打包會讓
  HTTP 請求逾時。交給 worker 是既有架構的自然延伸。
