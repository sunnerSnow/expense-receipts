# 0001. 定位為公司報帳工具,放棄個人模式與財政部 API

- 狀態:Accepted
- 日期:2026-07-28

## Context(當時的情境)

最初構想是「拍照記錄發票」的雙用途工具:公司報帳 + 個人記帳,個人側要結合載具
(雲端發票自動同步)。查證後發現:財政部電子發票整合服務平台的「查詢載具發票明細」
API 自 2023 年起僅限公司(營業人)名義申請,授權最長 3 年且需定期重審。
使用者明確表示不願走公司申請這條路。

個人雲端發票的痛點在於店家通常不印證明聯 —— 沒有 API 就只剩「手動下載 CSV 匯入」
或「結帳改索取紙本」,體驗大打折扣;而公司報帳的單據本來就是實體憑證拍照,
完全不依賴政府 API。

## Decision(決定)

本專案定位為**公司報帳單據管理工具**:拍照上傳、辨識、分類、月結匯出。
個人記帳模式與載具同步整個擱置;不商品化、不做多租戶、不做簽核流程。

## 理由

- 公司報帳流程(實體憑證 → 拍照)不依賴任何外部審核,三個 Phase 全部自己可控
- 個人模式失去自動同步後價值大減,不值得撐大範圍
- 自用工具,範圍越小越快能真的用起來

## Consequences(代價與收穫)

- 收穫:零外部依賴;範圍收斂,Phase 1 即可日常使用
- 代價:個人消費記帳需求未被滿足;若未來要加回,自動同步仍無解(除非申請 API)

## 保留的門

`receipts.context` 欄位(company / personal)保留,未來加回個人模式不用改表。

## 被否決的替代方案

- 公司名義申請財政部 API:使用者明確不走;且授權綁三年重審,行政負擔與自用規模不成比例
- 個人模式用 headless browser 抓電子發票平台:驗證碼 + 改版風險,維護成本高於價值
- 雙軌並行(公司 + 個人 CSV 匯入):範圍過大,延後可用時點
