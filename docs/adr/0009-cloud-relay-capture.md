# 0009. 離線拍收據改送雲端中繼站:Cloudflare Worker + KV 暫存,本機開機時拉回

- 狀態:Accepted(延伸 [ADR-0008](0008-offline-capture-queue.md);建單模組的位置由本 ADR 取代)
- 日期:2026-10-15

## Context(當時的情境)

ADR-0008 讓電腦沒開時也能拍照建單,但留下兩個代價:

1. **要打開 App 才會補送。** 而且要打開的時機是「連得到辦公室電腦」的時候 ——
   照片在那之前一直待在手機裡。
2. **照片只存在手機的 IndexedDB。** 使用者清除網站資料、手機壞掉或遺失,
   還沒送出的憑證就沒了。

2026-10-15 使用者提出「用 LINE 傳發票照片,讓後台直接整理,這樣就不用架在本機」。
討論後釐清:LINE 只是收件口,辨識、資料庫、憑證影像、核對、匯出都還是要有地方跑。
比較過三條路:

- A. 整套搬上 VPS(約 US$5/月,docker compose 不用改)—— 電腦完全不用開
- B. 只把「收件」放上雲端中繼站,主系統留在本機 —— 不用月費
- C. 維持 ADR-0008 的手機佇列

使用者選 B。接著又比較了「LINE + 中繼站」與「網頁 + 中繼站」,
選了**網頁**:LINE 會壓縮照片(憑證畫質)、要做帳號綁定、照片沒辦法附說明
(備註得靠「下一則文字」之類的規則),還要多申請一個官方帳號。
網頁版沿用現有的離線頁,改的只是「照片送去哪」。

不變的前提:

- 使用模式仍是「要用才開電腦」。核對(鐵律 3)與月結匯出還是在本機做
- 本機**不在公網上**(只透過 Tailscale 連),而且大部分時間是關著的
- 不付月費

## Decision(決定)

**手機把照片送到 24 小時開著的雲端中繼站暫存,本機 worker 開機時主動去拉回來,
走與上傳頁相同的建單流程。** 具體如下:

1. **中繼站**:新增 `apps/relay`,部署為 Cloudflare Worker,照片存 Workers KV。
   它只做收件與交件,**不辨識、不碰資料庫**:
   - `POST /uploads` —— 手機上傳(照片 + 備註 + 客戶端 UUID)
   - `GET /uploads` —— 列出待拉的件
   - `GET /uploads/:id` —— 取一件
   - `DELETE /uploads/:id` —— 本機確認收妥後刪除

   KV 的 key 就是客戶端 UUID;uploader、備註、MIME、拍攝時間放 KV metadata。
2. **手機端路由**:存檔一律先進 IndexedDB(與 ADR-0008 相同),存完**立刻**嘗試送出。
   目的地依序:
   - 連得到本機 → 本機(現行 `/api/receipts/offline`)
   - 連不到本機但連得到中繼站 → 中繼站
   - 兩邊都連不到(飛機上)→ 留在佇列,下次打開 App 再試

   佇列項目的刪除條件不變:**目的地明確回應收到才刪**。
3. **拉回**:本機 worker 啟動時拉一次,執行期間每 5 分鐘拉一次。每一件:
   下載 → 走共用建單流程 → 建單成功(或該 UUID 已存在)→ **才** `DELETE` 中繼站那一件。
4. **建單流程抽成共用 package**:`apps/web/lib/receipt-intake.ts` 搬到新的
   `packages/intake`(只給 Node 端用,與 `packages/auth` 同性質)。派工函式由呼叫端注入:
   web 傳自己的 `sendRecognizeJob`,worker 傳自己 pg-boss 的 `send`。
   上傳頁、補送端點、中繼拉回三條路共用這一份。
5. **兩把鑰匙,用途分開**:
   - **上傳憑證**(手機 → 中繼站):手機連得到本機且已登入時,向本機
     `/api/relay/credential` 領一張以 `RELAY_SECRET` 做 HMAC 簽章的憑證
     (內含 userId 與簽發時間,效期 90 天),連同中繼站網址存進 IndexedDB。
     中繼站用同一把 `RELAY_SECRET` 驗章;**uploader 以憑證為準,不信任請求本文**。
   - **拉取權杖**(本機 worker → 中繼站):另一把 `RELAY_PULL_TOKEN`,
     只能列出、取件、刪除,不能上傳。
   - 簽章與驗章只寫一份,用 WebCrypto(Node 與 Workers 都能跑),
     放在 `packages/auth` 的獨立子路徑,不會連帶 import `node:crypto`。
6. **整個功能是選填的**:本機沒設 `RELAY_URL` 時,手機不領憑證、worker 不拉取,
   行為與 ADR-0008 完全相同。
7. **不改資料庫 schema**:中繼站的件建成單據後,就是一般的 `source='ai'` 單據。

## 理由

- **拉而不是推。** 本機不在公網上、大部分時間關著。要中繼站推過來,就得替本機開
  公網入口,而且推不到關著的機器。改成本機拉,只需要出站連線,Tailscale 那套
  「登入頁不在公網上」的安全前提完全不變。
- **KV 而不是 R2。** 照 2026-10 查到的資料,R2 開通前要先綁付款方式(仍有免費
  額度)。KV 免費方案每天 1,000 次寫入、100,000 次讀取、總量 1 GB、單筆上限
  25 MiB,自用量綽綽有餘。每 5 分鐘拉一次等於每天 288 次 list,也在每天 1,000 次
  上限內。中繼站的件拉回後就刪,1 GB 不會累積。
- **先進 IndexedDB 再送,而不是直接上傳。** 保存只有一條路:中繼站掛了、沒訊號、
  超過當日額度,照片都還在手機裡,不會因為「直接上傳失敗」而遺失。
- **冪等沿用客戶端 UUID。** 同一件重送到中繼站是覆寫同一個 key,不會變兩件。
  本機用 `receiptExists` 擋重複。KV 是最終一致的,刪除後短時間內可能還列得出來,
  重複拉回時 UUID 會擋下,只是再刪一次,不會產生第二筆憑證。
- **中繼站的件要等本機落地才刪(鐵律 6)。** 本機存好之前,中繼站那份是這張憑證
  **唯一**的副本,手機佇列在送達中繼站時就已經刪了。
- **建單抽成 package 是 ADR-0008 同一個理由的延伸。** 原本兩條路共用
  `lib/receipt-intake.ts`。現在多了 worker 這一條,而 apps 之間不能互相 import。
  如果 worker 自己再寫一份,遲早有一邊忘了 `pending_review`(鐵律 3)或忘了把派工
  失敗寫回 DB。
- **拉取放 worker,不放 web。** worker 本來就是背景程序,有資料庫、pg-boss 與
  `UPLOAD_DIR`。在 Next.js 程序裡跑定時輪詢,web 就變成半個 worker,
  啟動與關閉的時機也不歸它管。
- **上傳憑證不共用 `SESSION_SECRET`。** 中繼站在第三方平台上。萬一 `RELAY_SECRET`
  外洩,最壞情況是有人往中繼站塞照片,而那些照片都會落在 `pending_review`,不會
  自動入帳。如果共用 `SESSION_SECRET`,外洩就等於可以偽造任何人的登入。
- **上傳與拉取分兩把鑰匙。** 手機上的憑證只能上傳、不能讀。就算手機遺失,
  別人也拿不到中繼站裡其他照片。

## Consequences(代價與收穫)

- 收穫:手機有訊號時,照片**拍完就離開手機**,不再因為清除網站資料或手機遺失
  而丟掉憑證。
- 收穫:回辦公室**不用再打開 App 補送**。電腦開機、worker 一起來,照片就自己進來。
- 收穫:電腦開著、但手機沒連 Tailscale 時也送得出去,最多 5 分鐘內進到系統。
- 收穫:中繼站只收件不辨識,日後要加其他收件口(例如 LINE)可以接同一個中繼站,
  本機這邊不用重做。
- 代價:**多一套在 Cloudflare 上的系統要維護**:要有帳號、用 wrangler 部署,
  `RELAY_SECRET` 與 `RELAY_PULL_TOKEN` 要在本機 `.env` 與 Worker secrets 兩邊一致。
- 代價:**照片在拉回本機前暫存在第三方平台**(Cloudflare)。報帳收據不算高度機密,
  但這是事實,要知道。
- 代價:上傳憑證存在手機裡。手機遺失時要**換掉 `RELAY_SECRET`**,所有手機都要
  重新領憑證。
- 代價:手機要先在**連得到本機時領過一次憑證**,跟「離線頁要先線上開過一次」一樣。
  實作時要一併寫進 operations.md 的出發前檢查。
- 代價:辨識要等電腦開機才開始。中繼站不辨識,因為不想把 Gemini 金鑰放到第三方平台,
  而且辨識結果還是要回本機核對。
- 代價:「要打開 App 才會送」在 iOS 上依然成立(沒有 Background Sync)。
  差別是現在存檔當下就送,而拍照的人本來就開著 App。只有拍照當下沒訊號的件,
  才要等下次打開 App。
- 代價:KV 免費額度是**每日**上限。萬一超量,當天的上傳會失敗,照片留在手機佇列,
  隔天自動再送,不會遺失。

## 被否決的替代方案

- **LINE Bot 收件**:LINE 會壓縮照片,而照片就是報帳憑證;要做 LINE 帳號與系統帳號的
  綁定;照片沒辦法附說明,備註得靠「下一則文字歸給上一張」這類規則;還要多申請
  官方帳號。真正多出來的好處只有「不用打開 App」。日後真的想要,可以接到同一個
  中繼站。
- **整套搬上 VPS(方案 A)**:能根治,而且 docker compose 不用改,但每月要錢。
  使用者目前的量不值得。本 ADR 不排除日後這樣做;搬上 VPS 之後,中繼站可以直接
  停用(`RELAY_URL` 留空)。
- **Cloudflare R2 存照片**:開通要先綁付款方式。這個量用 KV 就夠了,KV 的單筆上限
  (25 MiB)也比上傳頁的上限(15 MB)大。
- **中繼站主動推送到本機**:本機不在公網上,也大多關著。要推就得開公網入口,
  而且推不到關著的機器。
- **上傳憑證共用 `SESSION_SECRET`**:中繼站在第三方平台,外洩代價從「被塞照片」
  放大成「可以偽造登入」。
- **在 web 程序裡定時拉取(instrumentation)**:web 不是背景程序,多實例或重啟時
  的行為也不好掌握。worker 本來就負責這類工作。
- **中繼站順便做 AI 辨識**:Gemini 金鑰要放到第三方平台,而且 AI 結果還是要回本機
  人工核對(鐵律 3)。省不到事,只是多一處放密鑰的地方。
- **Supabase / Firebase 之類的後端服務當中繼站**:要多學一套平台,而且 Supabase
  免費專案閒置一段時間會被暫停。「要用才開」的使用節奏,正好會長時間閒置。
- **拿掉手機佇列、直接上傳中繼站**:飛機上、地下室這種完全沒訊號的情況還是存在。
  佇列也是「中繼站掛掉時照片不會掉」的保險。
